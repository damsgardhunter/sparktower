# Codebase audit — 23 September 2026

An independent pass over the whole repository: security, gaps, and what has to
happen before people are invited in. Evidence for every claim, and where
something was fixed during the audit it says so and names the test that now
holds it.

**Headline:** the security posture is genuinely strong — 560 routes, none
unmounted, every public write carrying a stated reason and a rate limit, an
append-only moderation log enforced in the database. One real vulnerability was
found and fixed. The things standing between this and a launch are mostly
**operational**, not code.

---

## 1. Fixed during this audit

### A private project's branding rendered for anybody — fixed

`GET /api/projects/:id/merch/preview.png` read the `projects` table by id with
no condition on it at all: no sign-in, no team check, no `isPrivate`. Anyone
holding a project id — and an id is in every URL its owner has ever pasted to a
collaborator — could have the server render that project's **name and logo**
into a PNG.

Private projects are the one thing this product tells somebody is not visible.

- Proven first, then fixed: `test/integration/merch-preview-privacy.test.ts`
  failed with a `200` where a signed-out stranger should have had a `404`.
- Fix: the route now 404s a private project to anyone not on its team — the
  same silence the rest of the product gives, rather than "it exists and you
  may not look". The owner still gets their preview; public projects are
  unchanged.
- Three tests now hold all three cases.

### Both image renderers were unauthenticated and unlimited — fixed

The preview and the Printful print file are both `GET`s, so the global write
floor never saw them, and neither had a limit of its own — while each
composites with `sharp` and lays out text with `opentype`, the print file at
4500×5400. On a single instance that also runs five background loops, an
unauthenticated loop over either is a cheap way to take the site down.

Both now sit behind a new `render` bucket (60 per 10 minutes, keyed by address
when nobody is signed in). Generous enough that a creator dragging a slider
never sees it; low enough that a script does.

### The fast test loop was hiding its own failures — fixed

`npm run test:unit` set no `SESSION_SECRET`, so every test touching the module
that **encrypts personal data at rest** died at import. The tests do run in CI
(`npm test` sets one), so this was not "untested in production" — but sixteen
always-red files in the loop a developer actually runs is how a real failure
hides in plain sight. Two fake, pinned secrets in `vitest.unit.config.ts`;
**1401/1401 unit tests now pass**, up from 1385 with 3 failing.

Fourteen files still report `(0 test)` there because they need `DATABASE_URL`.
They run under `npm test`. Worth either moving or marking, so the fast loop can
go fully green and stay that way.

## 2. Launch blockers

### The money model is not on the branch that deploys

`render.yaml` deploys **`main`**, auto-deploy on. Every commit of the
pay-per-use pricing work — wallets, day passes, priced outcomes, the $30 build
— is on `pay-per-use`, and the two have **diverged**: `main` is 13 commits
ahead, `pay-per-use` is 16 ahead.

They merge cleanly today. They will not stay that way, and the longer both move
the worse it gets. This is the single largest thing standing between the work
and a live product.

### Two migrations both numbered 0056

`migrations/0056_decision_simulations.sql` is committed and pushed;
`0056_project_currency.sql` is uncommitted in the working tree, and
`_journal.json` carries two entries at `idx: 56`. Drizzle numbers sequentially,
and `npm run db:migrate` is Render's **pre-deploy** step — the one that gates
whether the new build takes traffic at all. Renumber before either is merged.

### `e2e/capital-path.spec.ts` fails

The founder gets through the intake and `capital-profile-card` never appears.
Confirmed not to be the UI work: it fails identically with those changes
reverted. It sits on `shared/capital.ts` and `shared/phase-trees/systemize.ts`,
both of which arrived as uncommitted work on this branch and went in untested.

### Dev-only dependency advisories

`npm run audit:deps`: nothing high or critical **ships** — the gate passes. But
four high/critical sit in `vitest`/`vite`/`esbuild`, which run on your machine
and in CI with your tokens. Arbitrary file read and path traversal in the test
runner is worth a dependency pass before you hand the repo to anyone else.

## 3. What the audit checked and found clean

Worth recording, because "we looked" is most of the value of an audit.

| Area | Finding |
|---|---|
| Route guards | 560 mounted, **0 unmounted**. 17 writes reachable signed-out, every one with a written reason and a rate limit. **0 writes** with neither a limit of their own nor the global floor. |
| Authorization (IDOR) | 15 routes read a row by URL id; 14 check the caller through a helper. The 15th was the merch leak above. |
| Private-project leakage | 15 unauthenticated routes touch `projects`; all but the merch preview either require a deliberately published campaign, a capability token, or filter by privacy. |
| Secrets in git | Clean. Every `sk_live_` hit is a *redaction pattern* in code, not a key. `.env` is gitignored; only `.env.example` is tracked. |
| Dev bypasses | `/api/dev/set-tier`, `/api/dev/credit-wallet`, `/api/dev/reset-credits` and `SIM_DEV_ADVANCE` all hard-404 outside development **and** need a second explicit variable. `credit-wallet` additionally refuses a server holding live Stripe keys. This is better than most production codebases manage. |
| AI metering | Every model-calling route checks before it spends and charges after it answers. The two exceptions state why in the source, where the audit reads them. |
| SQL injection | The repo's own `sql-parameterized` check passes over every file. |
| Audit log | `moderation_log` refuses `UPDATE` and `DELETE` at the database, not in the application. There is a test that tries both and expects to be thrown out. |

## 4. Before you invite people

`docs/pre-deploy-user-testing.md` is a good list and most of it still stands.
These are the parts that are **stale**, and the gaps it does not cover.

### Stale — fix the document

- "331 app tests, 8 browser specs" → it is now **1401 unit + ~950 integration,
  and 34 browser specs**.
- Blocker 0 says "the last three rounds of fixes are uncommitted: unguarded
  writes and `/api/seed` removed…". That work shipped long ago. Replace it with
  the real blocker: **`pay-per-use` is not merged to `main`**.

### Not covered anywhere, and worth deciding before launch

- **Nobody is watching.** `ERROR_WEBHOOK_URL` is optional, and there is no
  uptime monitor wired (`npm run monitor:setup` exists, unrun). The first
  outage will be reported by a customer.
- **Restore has never been tested.** `docs/ops/backups.md` describes Render's
  backups; there is no record of anyone restoring one. An untested backup is a
  hope.
- **No staging.** `docs/env-contract.md` says so plainly — local, CI,
  production. Every first-time-in-production behaviour is discovered by a
  customer. That is a defensible choice at this size, but make it knowingly.
- **Support can now be handed over.** The customer console (`/admin/console`)
  covers refunds, passes, verification and project fixes with an audit trail —
  but only `PLATFORM_OWNER_EMAIL` can move money. Decide who the second
  operator is before you need one at 3am.
- **The account-deletion path.** `server/account-data.ts` exists; nobody has
  walked it end to end against a real account with backings, a company seat and
  a running season. That is a legal obligation, not a feature.
- **Rate limits have never met real traffic.** They are tuned by judgement.
  `RATE_LIMIT_EXEMPT_EMAILS` exists for your testers — set it, or your own
  testing will trip them and you will loosen the wrong thing.
